# Phase 4 integration readiness

Historical Phase 3D.2 handoff. Phase 4A now provides the frontend Auth foundation described in [AUTHENTICATION.md](AUTHENTICATION.md); the backend authorization and persistent-storage requirements below remain unimplemented.

Architecture review, 2026-10-21. This is a design handoff, not an implementation or approval to host recordings. Supabase, authentication and persistent storage remain absent.

## Current ownership and lifecycle

- `RecordingSession` owns a browser-memory reference to one uploaded recording and a synthetic demo. Refresh loses that reference; it does not delete the backend file. Annotations and drafts are component state, not server records. Navigation/discard prompts and JSON downloads are the current protection against loss.
- The local FastAPI store is process-wide, with no users or recording owner. Random recording IDs are opaque lookup keys, **not authorization**. Loopback/client/origin checks constrain local access but do not separate users or other local programs.
- Files are stored outside public directories with POSIX directory/file permissions, upload limits and a single operation gate. Default TTL is one hour from upload, with periodic/access cleanup, explicit deletion and shutdown cleanup. Crash leftovers can remain until restart. There is no encryption-at-rest or secure-erasure guarantee supplied by this application.
- `content_sha256` identifies exact original bytes across re-upload. Annotation imports also verify recording/channel/timing compatibility. A content hash is neither a user identity nor a permission token; it can reveal that two parties possess the same recording.

## Required changes before hosted use

| Boundary               | Required contract                                                                                                                                                                                                                                                                                                                                                                            |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity               | Validate authentication server-side. Establish an immutable owner or authorized research-project membership for every recording and annotation. Never trust client-supplied owner IDs. Define expired-session behavior that preserves unsaved annotations while requiring reauthentication for data access.                                                                                  |
| Authorization          | Protect upload, metadata, channel listing, samples, display, batch windows, CSV export and deletion. Every query must enforce the caller's access to the recording. Apply equivalent row/storage policies; a guessed ID, hash or object path must never grant access. Test cross-user reads, writes, imports and deletes explicitly.                                                         |
| Private objects        | Use private storage, opaque object keys, bounded uploads and controlled retrieval. Do not put EDFs, derived signals, exports or credentials into `public/`, browser build output or a public bucket. If temporary URLs are used, give them short lifetimes and scoped access. Keep service credentials server-side.                                                                          |
| Recording catalog      | Separate stable database identity from temporary worker IDs and original-byte fingerprint. Track owner, processing status, original checksum, source format, channel clocks, units and retention status. Preserve native samples and calibration; do not silently normalize uploaded bytes.                                                                                                  |
| Annotation persistence | Store recording association, author, schema version, point/interval type, native channel/sample anchors or recording-relative seconds, label/notes, timestamps and revision. Define optimistic concurrency and explicit conflict handling. Distinguish a locally edited draft from a successfully saved revision. Preserve JSON portability without allowing imports to claim another owner. |
| Processing             | Replace the shared local store/gate with bounded per-job worker isolation, quotas and tenant-aware queues. Add enforceable CPU/memory/time limits for untrusted parsing, cancellation and cleanup. Preserve the existing windowed provider interface instead of loading full recordings into browser memory.                                                                                 |
| Caching/logging        | Scope caches and background jobs to authorized ownership. Avoid raw headers, filenames, channel labels, notes, payloads, signed URLs and tokens in routine logs. Invalidate caches after revocation/deletion. Current `no-store` responses alone are not a complete privacy architecture.                                                                                                    |
| Deletion               | Specify recording deletion across original objects, derived caches, annotations, queued jobs, download links and indexes. Account deletion must handle owned/shared research records under an explicit retention policy. Define backup retention and restoration behavior; do not promise immediate secure erasure from all media.                                                           |
| Frontend               | Replace localhost-only upload gating with an explicit authenticated data provider and recoverable upload/processing state. Keep the account-free synthetic demo isolated from private recordings. Do not repurpose the local privacy claims for hosted behavior.                                                                                                                             |

## Patient-data and release risks

EDF bytes may contain patient/recording identities and acquisition dates even though the current API withholds those header fields. Original channel names and annotation free text can also identify people. Withholding metadata is not de-identification. Explicitly address research consent, access roles, retention, export sharing, backups, incident response and the intended jurisdictions before accepting sensitive data. Determine applicable obligations with the responsible institution; this report is not a compliance certification.

Before a cloud preview: review the hosted threat model, verify account/tenant isolation and private object policies with negative tests, test upload/parser limits and session expiry, exercise deletion and backup behavior, and repeat the independent scientific suite through the new storage/provider path. Clinical claims remain unsupported.

The current windowed data model, native channel clocks and portable annotation schema provide useful integration seams. The local product is ready for a scoped Phase 4 design discussion after review of `PRODUCT-VALIDATION.md`; it is **not ready to expose the existing backend publicly**. No cloud changes were made in Phase 3D.2.
